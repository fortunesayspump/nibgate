# Onchain escrow

For runs where the budget must be enforceable by contract rather than by promise, Dr. Nib escrows the cap on Arc using stock [ERC-8183 (Agentic Commerce)](https://eips.ethereum.org/EIPS/eip-8183) plus a splitter contract. Funded runs are enabled on testnet and mainnet. A complete mainnet wallet-to-report-to-refund flow was recorded on 15 Oct 2026; independent escrow review remains open.

<Callout type="info">
The public testnet and mainnet flows require escrow before research starts. Ledger-only mode is for development; it does not represent a payment or onchain refund.
</Callout>

<Callout type="warning">
**Operator prerequisite:** escrow is only enabled when the dr-nib service has the keeper key set (`ESCROW_KEEPER_KEY`, also read from `NIBGATE_KEEPER_PRIVATE_KEY`) — plus `ESCROW_CORE` / `ESCROW_SPLITTER` on mainnet, which has no built-in defaults. Without the keeper key the escrow endpoints answer `501`. Browser runs have completed create → fund → run → complete → split on both testnet and mainnet. External review remains open.
</Callout>

## Roles

| Role | Who |
|---|---|
| Client | your wallet — funds the job, receives refunds |
| Provider | the run's splitter contract — receives the deposited budget on completion, then divides it |
| Evaluator | the Nibgate keeper — attests completion against the run ledger (a JEV-gated evaluator contract is the planned successor) |

## Lifecycle

```txt
Open → Funded → Submitted → Completed → split
  │       │          │            │           │
  │       │          │            │           └─ operator (spent−1%), treasury (1%),
  │       │          │            │              client (remainder), atomically
  │       │          │            └─ keeper complete(reportHash), hook-free
  │       │          └─ keeper relays submit(reportHash, spent)
  │       └─ you sign setBudget + approve + fund
  └─ you sign createJob(provider=splitter)
```

 1. **Open** — your wallet opens the job at review (provider = splitter, evaluator = keeper). The backend supplies the parameters and registers the job ID from your confirmed transaction receipt.
 2. **Fund** — after opening the job you sign `setBudget` + `approve` + `fund`, picking any amount from the plan estimate up. The deposit is one-shot (the core flips Open→Funded; no top-ups ever). Approve is then gated: the run only starts once the job reads Funded for at least the estimate, and the working cap aligns down to what landed.
 3. **Run** — stages meter spend in the offchain ledger, exactly as without escrow. Pause at cap on an exhausted deposit ends (report kept) or restarts bigger as a new run — raising past the deposit is rejected everywhere.
4. **Submit** — the worker submits `(reportHash, spentUsdc)` through the splitter (the provider is a contract and cannot sign, so the keeper relays).
5. **Complete** — the keeper completes with the ledger-attested spend.
6. **Split** — the backend relays the keeper-signed attestation immediately at settle (and `POST /escrow/complete` re-runs it idempotently): earned share minus 1% to the operator, 1% to treasury, remainder to your wallet — one atomic transaction, hash stored as `splitTx`. `split()` stays permissionless, so anyone can also execute a signed attestation directly.

Why a splitter instead of the spec's hook: in the reference implementation `complete()` transfers the full budget *before* `afterAction` fires, so a hook can observe the payout but never redirect it. Setting the provider to the splitter keeps the escrow contract 100% stock.

Rejected or expired jobs refund in full with no fee. After expiry, `claimRefund` is permissionless: anyone can trigger it, so funds are never hostage to a backend being alive. One upstream quirk to know: if client and evaluator are ever the same address, the core checks the client branch first, so use distinct roles.

Each wallet transaction must have a successful receipt before the next step starts. The job ID comes from the matching `JobCreated` event in that transaction, so concurrent runs cannot select each other's jobs.

New job parameters are withheld if the contracts are missing, the RPC is on the wrong chain, or the keeper has less than 0.02 native USDC for settlement. Funded settlements retry every minute, with failed attempts moved behind other pending jobs; never-funded Open jobs do not occupy the retry queue. The owner can also retry from the receipt. A completed job with an unexecuted split remains retryable; a reverted transaction never counts as confirmation.

## Backend endpoints

| Endpoint | Does |
|---|---|
| `POST /v1/runs/:id/escrow` | return parameters for your wallet to open the job after a model-generated plan is ready (`planned` only); unavailable-model placeholder plans cannot be funded |
| `POST /v1/runs/:id/escrow/register` | register the wallet-created job after validating its onchain client and provider |
| `GET /v1/runs/:id/escrow` | local record + live onchain status |
| `POST /v1/runs/:id/escrow/complete` | keeper submit + complete with ledger spend, then relay of the split; returns the split signature and `splitTx` |
