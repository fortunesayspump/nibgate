# Dr. Nib confidential-worker implementation checkpoint

This is an **isolated, local-only branch of the existing Dr. Nib worker** based on Nibgate commit `11f8b806cfb8152ae0be133728e24941f979de4b`. It is not deployed, does not process confidential customer runs, and must not be described as operator-blind yet.

## What the code does now

- `backend/src/privacy/guard.js` and calls in the existing `worker.js`, `tools/executor.js`, `sources/routes.js`, `routes/runs.js`, and `routes/exports.js` block nonlegacy runs before the ordinary plaintext worker, source parser, tools, recovery queues, and export renderer can use them. Legacy rows with object metadata and no privacy marker remain compatible; this absence is **not** an authenticated legacy classification.
- `POST /v1/runs/:id/sources/encrypted` is a wired ciphertext-only intake seam. It expects `{envelope,attestationEvidence,proofOfPossession,clientNonce}`. The supported envelope is now **HPKE v2** (P-256/HKDF-SHA256/AES-128-GCM through the vetted `hpke` package), so the attested recipient can actually decrypt. Its authenticated data binds tenant/run/object/revision/purpose and the SHA-256 digest of the recipient public key. The API rejects unexpected envelope fields and requires a positive, context-bound attestation/key-possession verdict before storing. In production the verifier never supplies that verdict. If a future verifier is enabled, this route stores only the sealed JSON bytes in the private source bucket and ciphertext metadata in `ResearchStep.output`. A unique R2 key prevents a duplicate object ID from overwriting an existing object. No URL fetch, OCR, text extraction or model call occurs on this route. `GET /v1/runs/:id/sources/:sourceId/encrypted` returns sealed bytes only, after owner authentication and a storage digest check. The client-side attestation/key-release flow remains unwired.
- **The production recipient verifier deliberately always returns 503.** A requester cannot enable confidential uploads with an environment flag or a fake verdict. `POST /v1/runs` still rejects `privacyMode:'confidential'`. The encrypted route can only be exercised with a synthetic confidential row and test-injected verifier; it is an implementation seam, not a usable feature.
- `backend/src/privacy/phala-quote.js` is a guest-side Phala dstack quote-request adapter. It hashes a 32-byte client challenge and ephemeral public key into 32 bytes of `reportData`, uses the documented `DstackClient('/var/run/dstack.sock').getQuote(...)` API, and rejects the simulator. It only **obtains** evidence. It does not verify the TDX quote, event log/RTMRs, TCB, certificate chain, app-compose policy, endpoint key binding or freshness. Production does not invoke this adapter yet; the SDK is not installed in this patch. It imports dynamically and fails closed if absent.
- `backend/src/privacy/private-repository.js` is a measured-worker-only adapter for the existing Prisma `ResearchStep.output` and `ResearchReport.markdown` fields. It uses Node's AES-256-GCM with tenant/run/object/revision/purpose as authenticated associated data, keeping synthetic canaries out of captured DB writes. A key provider must release a key only inside a verified measured worker. This adapter is not yet connected to `runPlan`/`runExecute`, and other direct-write fields (brief, decisions, claims, events, exports) remain plaintext in the legacy pipeline.

## Why the existing worker cannot simply move to Phala

`attachSource` currently parses bytes and URLs on the API before the worker; `ResearchRun.brief`, `ResearchStep.output`, reports, events and decisions store plaintext; `llm/provider.js` sends prompts to OpenRouter. `jev/decisions.js` builds a JEV source-judging state from the research question plus each source URL, title and up to 650 characters of text, including supplied uploads; intake answers and worker continuation context can also reach the ordinary hub JEV client. JEV, network tools, logs, queues, retrieval and export rendering therefore cross the boundary. Each must be converted to ciphertext outside the measured Phala VM. Existing Railway services may continue as scheduler/transport, but neither Railway private networking nor R2 access controls prevent Nibgate operators from reading plaintext held there. The current browser frontend is mutable by Nibgate, so client-delivered code and key policy must be pinned/verified independently for an operator-blind claim.

## On-demand Phala CVM policy sketch (not deployed)

A separate conventional controller would queue **ciphertext-only** work, use a bounded concurrency lock to start an already-provisioned Phala CVM, wait for the guest app to be ready, require a fresh attestation and client key-possession handshake, dispatch the existing worker pipeline inside the CVM, checkpoint encrypted state, drain active stages, then request graceful shutdown after a measured idle interval. A stopped CVM cannot wake itself. Duplicate and retry jobs need stable IDs. The local policy prototype has an admission/idle runtime ceiling and start lock, but a long active job can exceed it. Production needs an external provider-level hard spending ceiling and recovery for stuck jobs, boot loops and uncertain shutdown, rather than assuming that gifted credits cap spending. It checks an injected attestation gate for each job, but no real verifier is installed. Pending key release cannot be automated by an offline client until a separately authorized key policy exists. Do not create or destroy a CVM per request; retained disk still incurs storage charges while stopped. No start/stop API call, account setup, wallet action or charge was made here. Actual boot latency and minimum viable idle interval need measurement on authorized hardware.

The hybrid decision schema and synthetic evaluation plan are in `CONFIDENTIAL-DECISIONS.md`; provider and threat-model analysis is in `PHALA-PRIVACY-EVALUATION.md`. `backend/src/privacy/phala-ai-port.js` and `minimized-jev.js` are local interfaces only, not current worker imports.

## Next gates, in order

1. Specify a client-held document key and independently verified Phala attestation handshake. Pin expected measured OS, canonical `app-compose.json` hash, workload image, quote signing chain/TCB, fresh nonce, debug/SSH/log policy and ephemeral recipient key. Challenge the guest to **prove possession** of that ephemeral key; a quote containing its hash alone does not do this. The dstack guest SDK only requests evidence. The client must verify it **before** releasing or wrapping any key. Phala Cloud KMS and an on-chain policy solely controlled by Nibgate do not by themselves satisfy the operator-blind claim.
2. Put source parsing/OCR, prompt construction, JEV-equivalent decisions, checkpoints, reports, and export generation inside a measured VM running the **existing** Dr. Nib pipeline with an encrypted repository adapter. Do not send private context to the current OpenRouter or hub JEV. Decide and test the attested model/provider path separately; the current OpenRouter router/model name does not establish which downstream processor sees a prompt or whether it is confidential. If Phala Private AI is selected, its official attested-routing docs require explicit `provider: { aci_verified: true, zdr: true }` constraints, attestation/TLS verification and a verified receipt; an unconstrained OpenAI-compatible call is not an attested call. The advertised `@phala/aci-verifier` client/receipt flow still needs integration and real negative tests before accepting results; the provider ZDR setting is a policy assertion, not cryptographic proof of non-retention. Never relax the constraints on retry. JEV/TypeSafe-equivalent quality and semantics still need testing. The current OpenRouter public ZDR catalog lists TypeSafe JEV 1.13/1.14, but a future trusted-provider route would still need exact endpoint pinning, `provider.zdr=true`, `data_collection=deny`, `allow_fallbacks=false`, `require_parameters=true`, and negative tests that these constraints cannot be silently ignored or dropped on retry. ZDR is a retention policy and **does not** mean the Nibgate hub or its operators cannot see the plaintext sent through that path.
3. Make run creation and all API/DB/R2/Redis/log/tool paths ciphertext-safe. Make `privacyMode` classification tamper-resistant; the current JSON metadata guard cannot defend against an operator changing it. Support legacy data without silently migrating or deleting it.
4. Run full existing worker integration tests with harmless synthetic canaries across recovery, retries, pause/resume, spend, report versions, exports and errors. Inspect actual DB, R2, Redis, stdout/traces and outbound HTTP for canaries. Then use real hardware to test quote verification, revoked/stale/debug measurements and policy/upgrade governance before turning on private mode.

## Local verification

`node --test dr-nib/backend/src/privacy/*.test.mjs` currently passes 41 tests, covering synthetic ciphertext handling, genuine local HPKE seal/open and tamper/wrong-recipient rejection, encrypted Prisma-field writes, no side effects when the real verifier rejects, malformed contexts, compensation after DB failure, the guard, Phala quote request binding and a fake-API on-demand policy. It does not execute a Phala VM, HTTP routes with a real DB, or the full Dr. Nib worker. The repository specifies Node 22; this isolated shell has Node 24. The HPKE test currently resolves an inspected temporary local package copy; pnpm package/lockfile wiring has not completed, so this checkout is not yet reproducible on a clean machine. Full pnpm/Vitest/Postgres verification was not completed. This checkout has not been pushed or deployed.
