# Phala recipient attestation gate

This adapter is an **unconfigured, fail-closed integration seam**. It has not been exercised against a real Phala CVM or verifier, and no customer key or private source should be released based on local synthetic tests. No measurement, verifier address, SPKI pin or KMS identity is supplied by this repository.

## Verification contract

`backend/src/privacy/phala-verifier.js` sends the exact dstack SDK evidence to an independently trusted dstack-verifier `/verify` service: either `{attestation}` or `{quote,event_log,vm_config}`. It does not implement quote cryptography. The `createPinnedDstackVerifier` transport requires ordinary WebPKI hostname validation **and** an out-of-band SHA-256 pin of the verifier TLS SubjectPublicKeyInfo. It uses a dedicated one-shot TLS connection so no pooled socket can skip that pin. It rejects non-HTTPS, redirects, malformed responses, oversized responses, timeouts and pin mismatch. The endpoint, SPKI pin and pinned verifier image digest must be reviewed independently of the untrusted Phala guest. A pinned TLS key authenticates the service endpoint; it does not prove the service is running a correct or current verifier build.

The gate requires successful hardware quote verification, event-log replay, OS image-to-boot-measurement verification and TDX ACPI verification; `dstack-tdx`, `UpToDate` TCB with no advisories, exact independently approved app ID, OS and compose hashes, and exact KMS identity. A trusted controller may also pin the instance ID, but should authenticate each new on-demand instance before approving it. dstack's default app ID may just be a truncated compose hash, so the app ID pin alone cannot establish who deployed the CVM. It rejects `os_image_is_dev:true` or a missing field. Modern TDX lite evidence reports `os_image_is_dev:null`; this is accepted only with an independently reviewed production OS image hash and `reviewedReleaseControls.productionOsImage:true`. Null is **not** itself proof of production. The gate compares the verified 64-byte `report_data` to `SHA-256("drnib-phala-session-v2\0" || 32-byte client nonce || raw 16-byte session UUID || exact 65-byte uncompressed P-256 ephemeral public key) || 32 zero bytes`. A new client nonce must be generated by the relying party, stored with an expiry, and atomically consumed once only after policy and key-possession verification. A live HPKE encrypted-challenge handshake must prove that the responding guest holds the bound ephemeral private key. A quote that merely names a public key does **not** prove possession.

`reviewedReleaseControls` must assert all five controls: production OS image, SSH disabled, debug disabled, plaintext logs disabled, and images pinned by digest. These assertions are **not** derived from the quote. Before setting them true, an independent reviewer must inspect the exact measured OS, app-compose file, container images, boot parameters, service configuration, debug endpoints, shell/SSH access, and stdout/stderr/tracing/error paths, then approve their hashes. If a release changes, approval and measurement pins must be updated deliberately; missing or mismatched values reject. The verifier itself rejects debug-mode TDX evidence, but it cannot infer whether application code logs private records or exposes an SSH service merely from the returned compose hash without a reviewed release mapping.

## Production prerequisites

1. Pin a reviewed dstack-verifier source revision and immutable service image digest. Validate its `/verify` response schema and negative cases against the exact deployed dstack guest/SDK versions. Do not use a moving `latest` tag or a public verifier response as the trust root.
2. Operate the verifier under an independently controlled security boundary. Record its HTTPS URL, TLS SPKI SHA-256 and rotation process in relying-party release policy. Never copy a pin, compose hash, OS hash or KMS identity out of the same guest response being evaluated.
3. Build and review the exact production OS and digest-pinned app-compose release; establish its app ID, OS image hash, compose hash, KMS identity, and absence of debug, SSH and plaintext log paths. Keep the review evidence with the release policy. Do not insert placeholder measurements to make a test pass.
4. Wire the client-held nonce store and HPKE possession handshake on the relying-party side. Do not accept a Boolean or proof object supplied by the guest as possession. Verify transcript binding to the same nonce, session ID and public key before returning the callback result.
5. Run real Phala hardware tests for a valid quote and negative cases: corrupted quote/event log, altered nonce/session/key, mismatched OS/compose/KMS, stale/revoked/advisory TCB, debug or simulator launch, expired/used nonce, invalid HPKE proof, TLS hostname/pin failure, verifier outage, and release rotation. Document the observed measurements and verifier build. Maintain a stop switch that blocks private key release.
6. Verify that the client running this gate and its release policy cannot be silently replaced by the operator from whom privacy is sought. Mutable Nibgate-served browser JavaScript alone cannot establish an operator-blind key-release boundary.

`node --test dr-nib/backend/src/privacy/phala-verifier.test.mjs` covers synthetic policy and malformed-input behavior only. No live quote, quote signature, RTMR, TLS connection, hardware debug flag, customer record, or deployment is verified by that suite.

## Browser release boundary

This Node adapter can pin the HTTPS verifier's TLS SPKI. Standard browser APIs do not expose an equivalent per-request TLS SPKI check, and official dstack-verifier JSON responses are unsigned. A Nibgate-operated API that forwards a verifier's unsigned `{is_valid:true}` response cannot serve as an independent browser trust root. A viable browser path is to call a **fixed, independently operated verifier origin directly** over browser-validated HTTPS, with appropriate CORS, and to accept the verifier operator plus browser WebPKI/DNS as explicit trust roots. The browser must apply the same strict verdict/release policy, nonce freshness and live HPKE possession checks locally before encrypting any source. The client build and approved release policy must be pinned or distributed independently of mutable Nibgate-served JavaScript, or an operator can replace the checks. A signed verdict with an independently pinned verifier signing key is another possible design, but is not mandatory for a direct trusted HTTPS channel. No independently operated full dstack verifier origin with appropriate CORS is configured in this prototype; this route must remain blocked until one is provided and tested.

For a **fixed-boot local demo without an online verifier service**, `frontend/src/lib/dr-nib-private-qvl.ts` provides a second narrowly scoped browser route: a reviewer first runs the official full dstack verifier against the exact live V1 attestation and pins its quote measurements plus reviewed app/OS/compose/KMS identity in a short-lived local client release. The browser extracts the exact quote from that same attestation and uses official Phala QVL for fresh Intel quote verification and strict measurement comparison. This avoids trusting a guest-supplied verifier verdict and does not require a new signing key for a static, independently hash-pinned local client build. A reboot, new on-demand instance, runtime RTMR3 extension or expiry may invalidate the pins and must fail closed until independently re-reviewed. See [PHALA-BOOT-PINS.md](PHALA-BOOT-PINS.md) for the exact review, pin and restart procedure. This path does not authorize a mutable Nibgate-hosted browser bundle.

Phala documents a public [quote-verification API](https://docs.phala.com/phala-cloud/phala-cloud-api/attestations) at `https://cloud-api.phala.com/api/v1/attestations/verify`, but its `{hex}` input and `{success,quote.verified}` output do **not** perform the dstack application event-log, OS image, compose and KMS verification this gate requires. It must not be substituted for the full dstack-verifier. No public, full dstack-verifier HTTPS origin with the requisite schema was found in official documentation. The upstream [server source](https://github.com/Dstack-TEE/dstack/blob/next/dstack/verifier/src/main.rs) exposes self-hosted `/verify` and `/health` over Rocket without a CORS layer; browser use would require independently governed HTTPS termination and carefully scoped CORS at that independent origin.
