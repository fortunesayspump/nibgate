# Phala wake-on-contact (coded, default disabled)

This is a local, single-process adapter for an **already provisioned** Dr. Nib CVM. It creates no CVM, account, wallet action, deployment, or API key. It has made no live Phala call. A stopped CVM cannot receive contact itself: an ordinary broker must receive the request, start the CVM, and keep private inputs sealed until a fresh independent attestation passes.

The ordinary Dr. Nib broker now has a disabled-by-default production bootstrap behind `DRNIB_PRIVATE_WAKE_ENABLED=true`. When enabled, the normal `createApp()` path constructs the pinned official `@phala/cloud@0.4.0` client, lifecycle port and wake controller only after every required configuration value validates. A missing package, credential, reviewed release policy, pinned verifier or CVM ID leaves all private routes closed. `createApp({privateWakeController})` remains a synthetic-test injection seam. No live Phala lifecycle call has been made in this cloud checkout. Private draft admission checks the owner and three-run limit before `ensureReady()` may start billable compute. Each authenticated forwarding request holds a unique run-bound lease through capability signing and guest fetch; its AbortSignal cancels fetch on a trust or deadline stop.

Before each forwarded request, `phala-broker-attestation.js` performs a fresh broker-side preflight: it opens a guest session with a broker-issued 32-byte nonce, appraises the full quote through a separately pinned dstack verifier, enforces exact reviewed app/instance/compose/OS/KMS and current TCB policy, encrypts a random HPKE challenge to the quoted session key, verifies the returned digest, and consumes the nonce once. This is a real coded verification path, with synthetic-only tests; no public quote has yet passed it on hardware. The browser's independently pinned fixed-boot/QVL verification and key proof remain required before it encrypts private content. Ordinary Nibgate-controlled broker configuration by itself cannot establish operator-blindness.

The required bootstrap settings are `DRNIB_PRIVATE_WAKE_ENABLED=true`, `PHALA_CLOUD_API_KEY` (broker secret, never browser/guest), `DRNIB_PRIVATE_CVM_ID`, `DRNIB_PRIVATE_GUEST_BASE_URL` (HTTPS root), `DRNIB_PRIVATE_VERIFIER_URL` (HTTPS `/verify`), `DRNIB_PRIVATE_VERIFIER_SPKI_SHA256`, `DRNIB_PRIVATE_RELEASE_POLICY_JSON`, `DRNIB_PRIVATE_WAKE_IDLE_MS` (15,000–300,000), and `DRNIB_PRIVATE_WAKE_MAX_RUNTIME_MS` (30,000–3,600,000). Existing private-mode broker signing key, owner tenant allowlist and flags must also be present. The release-policy JSON must contain exact independently reviewed `expectedAppId`, `expectedInstanceId`, `expectedComposeHash`, `expectedOsHash`, `expectedKeyProvider:{name:"kms",id}`, and all five true release controls (`sshDisabled`, `debugDisabled`, `plaintextLogsDisabled`, `imagesDigestPinned`, `productionOsImage`). These values must come from a separately approved release/pin manifest; never derive them from the guest response. Debug SDK request logging is rejected. Do not enable flags merely because example values parse.

`backend/src/privacy/phala-lifecycle-api.js` accepts a caller-created official `@phala/cloud` JavaScript SDK client. It uses the documented `getCvmState({id})`, `startCvm({id})`, `watchCvmState({id,target:'running'|'stopped',...})`, `shutdownCvm({id})` for ordinary idle, and `stopCvm({id})` for emergency shutdown. The SDK, rather than this adapter, owns HTTP authentication and headers. `getCvmState` confirms the final state after each watch. Unexpected states fail closed. Restart and delete endpoints are deliberately unused. The emergency stop method is required; a deployment lacking it must stay disabled.

`backend/src/privacy/phala-wake-controller.js` exposes `ensureReady()`, `run(jobId, fn)`, `peekReady()`, `snapshot()`, `tick()`, `recoverUnknownStop()`, and `close()`:

1. After ordinary owner/run validation, `ensureReady()` takes a process-local start lock, starts a stopped CVM once, waits for provider `running`, then waits for a guest application health probe. It does **not** authorize key release or ciphertext forwarding. A private run can be created after this step only if creation itself contains no private plaintext or secret.
2. Before any private forwarding, call `run(opaqueJobId, async (jobId, signal) => { ... })`. Put capability signing and the **entire** guest request inside that callback. `run` checks current provider and guest readiness, reconciles an out-of-band stopped CVM by starting it again, then requires `verifyAttestation({jobId,generation}) === true` immediately before entering the callback. The coded verifier performs the fresh nonce, full quote/TCB/policy appraisal and live key-possession exchange before forwarding. A health probe, SDK `getCvmAttestation`, guest assertion, or `async()=>true` is not a verifier. Live verifier hosting, independently approved pins and hardware validation remain activation gates.
3. Concurrent requests share startup; each still gets a fresh attestation decision. An active lease prevents *idle* shutdown until the callback settles. `tick()` is armed automatically for idle and runtime deadlines. At the runtime deadline, it blocks new dispatch, aborts active callback signals, calls provider **force-stop** even if a callback is stuck, and confirms provider `stopped`. `close()` does the same instead of waiting indefinitely for a callback. A callback that ignores abort cannot turn its late result into success. This is a **per-process stop attempt, not an absolute provider billing cap**: an SDK/network failure or dead broker can leave the CVM running, and a broker restart loses in-memory usage. Unattended public release still needs an independent provider-level spending/stop policy, persistent accounting, and a distributed start/stop lease before multiple broker replicas may use this seam. An initial owner-only, manually watched synthetic test may instead use conservative bounded runtime and current account price/credit checks; the local stop attempt cannot guarantee a monthly bill.
4. A failed attestation or unknown provider/guest state quarantines the controller, aborts active signals, and immediately requests provider force-stop even if an active callback is stuck. An uncertain stop blocks new dispatch. `recoverUnknownStop()` may unblock only after a confirmed provider `stopped` state; if it is still `running`/`stopping`, it tries force-stop and confirms the result. Recovery never treats a network error as proof of stopping. `peekReady()` is only an in-memory status hint, not an attestation or fresh provider-state check. Callback code must honor its `AbortSignal` and checkpoint encrypted work. `run(jobId)` shares a promise for simultaneous identical IDs, so the broker passes a **unique run-bound ID per HTTP forwarding request** (run UUID plus fresh random UUID), never just a run ID; otherwise distinct session/report calls could receive each other's response. Only reuse an ID when a durable journal has verified that the request body and intended response are identical. In-memory duplicate suppression is not durable retry idempotency.

The lifecycle API credential is high-impact operational access. Keep it outside the guest and browser in a least-privileged broker secret store, limited to the one approved CVM/workspace and lifecycle scope if Phala supports such scoping. Never put it in logs, request URLs, source files, Docker images, or frontend bundles. The code reads it only when wake is explicitly enabled and fully configured. Actual key issuance/storage is an action-time account setup step; no credential is in this repository. Verify Phala's current key-scope controls before granting any access; do not assume fine-grained CVM scopes exist.

The reviewed-boot manifest is **not** updated from a restarted CVM's quote. Every fresh session rechecks evidence against the independently pinned client policy. If stop/start changes RTMRs or other pins, document release stays unavailable until a fresh independent full-verifier/source/config review and an approved pinned client build. Transparent wake across changed boots requires a separately governed verifier/update design, not trust-on-first-use.

Rollout order: deploy the disabled code to isolated testnet first. Resolve the exact SDK lockfile, run Node 22/privacy/Postgres/image checks, verify the hardware quote and independently reviewed testnet pins, then use only harmless synthetic documents for an owner-only Phala start/infer/stop test inside the approved spending limit. Check guest readiness, proof, encrypted DB/R2/log/network canaries, report recovery, idle stop confirmation and the next start's changed measurements. Keep testnet flags off if any gate fails. Mainnet requires separate review of the tested image digest, pins, browser build, spend and credential setup; do not copy testnet pins or assume a testnet pass authorizes private-data traffic. A credential-free hardware diagnostic passed V1 quote, session binding, QVL and full dstack verification on 2026-10-16; the CVM was deleted. Wake control, guest readiness in normal mode, paid AI, broker proof, and private sources were not tested.
