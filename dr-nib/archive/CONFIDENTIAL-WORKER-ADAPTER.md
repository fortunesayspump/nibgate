# Measured-worker encrypted state adapter

Status on 2026-10-16: local, un-applied follow-up implementation. A measured-guest plan + source-only short-writer slice has a separate opt-in `full-execute` HTTP route and synthetic tests. It is OFF by default behind `DRNIB_PRIVATE_FULL_ENABLED=true`, requires the additive schema migration, and has not been enabled or tested on live runs. Do not describe the full Dr. Nib worker as confidential.

## What exists

- `backend/prisma/migrations/0007_private_worker_objects` adds `PrivateWorkerObject` without changing legacy rows. No database migration was applied. Review, back up, rehearse, regenerate Prisma and test rollback before live use.
- `backend/src/privacy/private-worker-store.js` stores run state, source content, claims, decisions, reports and stage output as AES-256-GCM envelopes in that table. Associated data binds tenant, run, object, revision and purpose. The ordinary `ResearchRun` content columns remain null or a fixed encryption marker; stage rows carry only fixed kind/status/lease and an opaque pointer. The adapter checks the authenticated tenant, privacy mode, deletion marker and content-column markers before key release, then rechecks inside a transaction before writing. Failed or uncertain stage attempts cannot be automatically replayed by incrementing the attempt number.
- `backend/src/privacy/private-worker-events.js` persists only allowlisted fixed stage events or a pointer to a sealed private event. It does not use the ordinary eventlog or broadcast path. A separately audited private replay/stream route is still needed.
- `backend/src/privacy/private-worker-store.js` can initialize one sealed brief and supplied source atomically with the fixed `draft` → `planning` status. An identical retry is recognized after decrypting both records; a changed source or brief conflicts.
- `startSourceOnlyWrite(run)` checks the sealed plan checkpoint, exact one-source snapshot and original sealed browser report recipient, then atomically writes a sealed source-only marker and advances fixed `planned` → `running` status. Reentry requires the same state/source snapshot. `commitReport` rechecks run version, state/source revisions and the sealed write checkpoint under the advisory transaction before saving a sealed internal report. `completeSourceOnlyRun` then checks the sealed report/write checkpoint, original recipient and HPKE envelope, creates the external ciphertext-only `ResearchReport` and marks the run fixed `complete` in one transaction; the report ID is deterministic and exact-envelope replay is idempotent.
- `backend/src/privacy/private-plan-stage.js` runs one existing Dr. Nib stage. It uses the actual `llm/prompts.js` `planMessages` and `length.js` `resolveLength`, but calls only an injected attested `aiPort.infer`. It refuses malformed responses and provider failures instead of using the ordinary provider or placeholder plan. Its output is checkpointed before an atomic sealed-state/public-status commit, so a commit failure can replay the checkpoint without a second model call.
- `backend/src/privacy/private-write-stage.js` runs the source-only, at-most-1,200-word report branch using the existing Dr. Nib evidence, prompt and length modules; the opt-in guest composition requests 300 words under the present 1,200-token AI cap. It chunks each sealed source so late passages are present in the model prompt, seals the checkpoint and report, binds the browser report recipient in its input digest, and marks verification as unverified. It appends references but does not assemble the ordinary writer's abstract, so it is not full writer-equivalence. Longer sectioned reports and claim support verification remain closed. Both stage constructors require the branded `phala-aci-v1` AI port as an accidental-miswire guard; a marker alone does not prove attestation.
- `backend/src/privacy/private-verify-extraction.js` is a separate test-only slice of the existing verification stage. It follows `verifyReport`'s report chunking, factual-claim extraction prompt and cross-chunk sampling through the approved AI port, then seals candidate claims in the stage checkpoint with every status `unknown`. It checks state/source/report freshness between paid calls. It makes no support or originality verdict, writes no ordinary `ResearchClaim`, and is not part of the currently released 300-word composition; a protected judge and atomic individual-claim commit remain open.

## Required integration boundary

Instantiate store and event port per authenticated tenant **inside the measured guest**, after independent attestation and recipient-key verification. The bounded client-held key bridge in `CONFIDENTIAL-WORKER-KEY.md` keeps the key only in the active guest job. After a restart, the browser must rewrap the same retained key into a fresh verified session; if it has lost that key, checkpoints are unreadable and the user must start a new run. Railway never receives a plaintext key, and there is no server-held recovery key. The opt-in `full-execute` route accepts both HPKE source and client-held state-key envelopes. Its one-use session and execute journal fingerprint both encrypted envelopes before AI; the guest runs plan then the 300-word source-only writer and atomically persists fixed complete status with the browser-HPKE report. A lost response after that transaction can return the stable report ID through owner-bound job status. An interrupted or uncertain paid call is not automatically resumed even when the browser retains the same key. The ordinary `run.plan` and `run.execute` handlers remain forbidden for confidential rows until their entire direct-DB/provider/tool/event call graph is replaced.

The existing authenticated, same-origin broker has a narrowly gated HTTP contract, not a public MCP/OpenAPI operation:

- `POST /drnib-api/v1/private/sessions/:id/full-execute` accepts exactly `{runId,sourceEnvelope,keyEnvelope}`. Both are independently bound HPKE envelopes for the same run and guest recipient, with different object IDs. After the prior session proof, a completed request returns `200 {id:runId,version:1,encrypted:true}`; a still-active or uncertain request returns `202 {state:"processing"|"uncertain",runId}`. A conflicting ciphertext replay receives a fixed `409` error.
- `GET /drnib-api/v1/private/runs/:runId/job` returns only `{state:"not_started"|"processing"|"uncertain"}` or `{state:"complete",reportId}`. On completion, `GET /drnib-api/v1/private/reports/:id?runId=:runId` returns the bound HPKE ciphertext envelope for browser decryption. These reads require the authenticated run owner.
- The current route checks `DRNIB_PRIVATE_FULL_ENABLED=true` on both broker and guest, an exact test-tenant allowlist, guest readiness and migration presence. The measured guest now wraps the bounded and full AI calls in a local Postgres-backed reservation gate, which also requires the additive `0008_private_ai_budget` migration and configured price ceilings. This is admission accounting, not a provider-enforced hard cap or an infrastructure meter. Its live database, pricing and signed-usage behavior still need independent validation. Keep the route unpublished in MCP/OpenAPI until these controls and the remaining worker stages are reviewed.

## Remaining blockers

Search, fetch, data/tool loop, scoring, review, long writing, claim support/originality verification, exports, money/escrow, guidance, run detail/replay, MCP and interrupted-job recovery paths are not migrated. The atomic completion method validates ciphertext metadata but cannot decrypt browser HPKE ciphertext; only trusted measured guest code may call it after encrypting the same sealed report markdown. Global `AgentLesson`, file fallback and `QueryMemory` remain forbidden for private work; the plan, short-write and extraction runners do not import or invoke them. No live Postgres transaction, migration, CVM restart, browser key rewrap or paid-provider test has been run. Three narrow stages, only two of them on the opt-in HTTP path, do not prove end-to-end operator blindness.
